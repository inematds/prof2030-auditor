Lesson 4 · 25 min

Vibe Audit: reviewing the app the AI built

Building an app with AI has become easy: the manager describes it, and the tool delivers a website with a database in one afternoon. What the AI doesn't do on its own is close the doors. In this lesson you review one of these apps just by reading it: exposed secret, missing login, open database, and an old part. You diagnose; the team fixes.

Start the lesson

In this lesson you will

  1. 1The 4 layers that fail most in AI-built apps
  2. 2Where the auditor stops: diagnosis, report, and plan
  3. 3Using an AI agent to read the project without changing anything
  4. 4The Vibe Audit checklist, ready to copy

Objective: find an exposed secret, a route without login, a database without RLS, and a vulnerable dependency in an AI-built app, just by reading the project.

01 · The 4 layers of the vibe audit

Vibe coding is building an app by describing it to the AI in plain language. Review in this order. Click each layer.

A fifth layer, the site's security headers, comes in if the scope allows and there is time. For small and mid-size businesses, the 4 above cover most of it.

You only read the project (a copy or a repository released in the agreement). You do not test attacks on the live site.

02 · Where the auditor stops

The full method has 7 steps. The first 3 are yours; the others belong to the team that fixes, and you check at the end.

1. 1 · Diagnose

Read the project across the 4 layers. Nothing is changed. Whatever you could not see becomes "not verified".

Secret found: note the file, line, and first 4 characters. Never copy the whole key.

Findingapp.js, CONFIG.openaiApiKey: AI key in the browser (starts with FAKE…).

2. 2 · Report

For each finding: layer, file and line, proof, severity (the scale from lesson 3), and "not verified" when it applies.

Write so the owner understands: what happens if nobody does anything.

For CarlosAnyone who opens the app can copy the key and use the AI on Horizonte's account.

3. 3 · Plan

For each finding, the suggested fix and its risk: safe, moderate, or risky (could it break the app?).

Critical with a safe fix goes first. A risky fix only with the owner's OK and a test beforehand.

ExampleReplace the key: critical, moderate fix (the app stops suggesting products until the new key is on the server).

4. 4 to 7 · The team fixes, you check

The team or the vendor does the fixing: they make a backup, test on a copy, and apply one item at a time.

At the end, you repeat the diagnosis and deliver the "before × after" table. Without that check, the fix is not proven.

TableF2 · before: RLS off · after: RLS on, tested with two users · status: resolved.

03 · Templates to copy: checklist and request to the agent

The checklist guides you. The request is for an AI agent (Claude Code, Codex) to read the project without changing anything.

Vibe audit checklist
VIBE AUDIT CHECKLIST · <app> · <date> · reviewer: <name>
Mark: [ok] [finding] [not verified] — always with evidence

SECRETS
[ ] No key/password/token in any file that goes to the browser (.js, .html)
[ ] .env is NOT in the repository (nor in its history)
[ ] .gitignore lists .env and key files
[ ] Public variables (e.g., NEXT_PUBLIC_, VITE_) do not hold secrets
[ ] "service_role" or admin key is never in the front end
[ ] There is a spending limit at the AI provider

LOGIN AND ACCESS
[ ] Admin pages require login
[ ] Login is checked on the server, not just by hiding the button
[ ] API routes check the session and the role (admin vs. customer)
[ ] Admin has 2-step verification

DATABASE
[ ] RLS turned on for ALL tables with customer or order data
[ ] There is an "everyone sees only their own" policy
[ ] Anonymous user (anon) does not have permission to read/change everything
[ ] Tested with 2 different users (one does not see the other's data)

DEPENDENCIES
[ ] Dependency list checked (npm audit or equivalent)
[ ] No version with a known high-severity flaw (CVE)
[ ] The framework still receives fixes
[ ] Someone owns the updates

PUBLISHING
[ ] The app is public on purpose (the platform did not leave it open by default)
[ ] Test data is not real customer data

NOT VERIFIED (with reason): <...>
Request to the agent: read-only review
You will review the security of this project READ-ONLY.
Rules:
- Do not change, create, or delete any file.
- Do not run any command that accesses the internet, installs a package, or starts a server.
- Never show a full secret: only the file, line, and the first 4 characters.
- Anything you cannot confirm, mark as "not verified".

Review 4 layers and deliver a table
(layer | file:line | what you found | why it is a risk | severity critical/high/medium/low):
1. Secrets: keys, passwords, tokens in files sent to the browser or to the repository.
2. Login: admin or internal pages and routes without a server-side login check.
3. Database: tables without RLS, broad permissions for the anonymous user.
4. Dependencies: versions with a known vulnerability (cite the CVE if you know it; if you are not sure, say so).
At the end, list what stayed "not verified" and why.
Simulation: illustrative example
  1. Every finding has a file and line that you opened yourself (don't rely only on the agent).
  2. No secret appears in full.
  3. RLS was checked table by table.
  4. The "not verified" list exists, even if short.
  • Thinking the Supabase anon key is the problem: it is public by nature. The problem is the table without RLS.
  • Copying the agent's report without opening the files: agents also make mistakes and sometimes invent CVEs.
  • "Quick fix": you don't change anything. Fixing is the team's job, with backup and testing.

10 min

Done when: the 4 sentences have at most 25 words each and none uses an acronym without explaining it.

06 · Summary

Four layersSecrets, login, database (RLS), and dependencies. This is where AI-built apps fail the most.
Your roleDiagnosis, report, and plan. The team fixes with backup and testing; you check with the before × after table.
Why it mattersIn May 2026, researchers found about 380 thousand public apps built on vibe coding platforms, some 5 thousand with sensitive corporate data. Some of the platforms left the app public by default.
ScopeAssessment and triage of AI risks. This is not a pentest, nor incident response, nor a legal opinion. Sign of an intrusion, a leak, or a legal question: stop and escalate.
